# Windows setup flow: TD-05 proposal

**Status: TD-05 proposal by its owner (dnarsh), 2026-10-26, built on the supporting draft already merged here; runtime, GUI, accessibility and Windows evidence n=0.** This input helps TD-01 reconcile shared contracts and TD-06 design fixtures; it neither freezes schemas, routes, command names or visual design nor authorizes an operation. MdSiddiqx retains frontend design authority through TD-02/06. No runtime or visual implementation accompanies this document.

## Boundaries and defaults

Apply the [desktop authority contract](desktop-application.md), [module installation contract](modular-installation.md), [feature controls](capability-map.md), [model ownership](user-controlled-models.md), [provider/profile contracts](providers-profiles-and-sessions.md) and [frontend dossier](../frontend/README.md). The GUI presents the one fused engine's admitted outcomes through the existing Rust boundary; it owns temporary form/navigation state only. It cannot commit install records, grant permissions, decide readiness or introduce an engine loop, store or package resolver.

First launch offers **Continue with base only** as the primary, initially focused action, **Choose optional modules** and **Skip setup**. Both base-only and skip enter the ordinary workbench with settings accessible. Neither requires network, catalog availability, credentials or a generation model. A missing generation binding reads **Generation unconfigured**, with an explicit configure action; it does not make navigation or history unavailable. Setup completion never means model readiness.

All optional selections start empty. Existing user/project/ancestor configuration is not permission to fetch, import, load or activate referenced packages. No optional implementation, worker, model, external server or rich-editor payload enters the base merely because its control is hidden. Plain-text file/diff views and ordinary search remain available under the base contract; actual task execution still requires compatible explicitly selected generation and ordinary admission.

| User intent                 | Review and effect boundary                                                                                                     | Never implied                                                                                         |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| Install package             | Accept exact pinned package and complete required dependency closure; stage, verify and atomically record installed code       | Activation, model acquisition, provider login, runtime grants or unreviewed setup execution           |
| Enable installed feature    | Request configuration transition against current installed/config revisions; report requested and effective state separately   | Installation of missing dependencies, selection of a fallback service or download of weights          |
| Provision model assets      | Separately select local import or pinned download, source/digest, ownership, terms, bytes and destination                      | Inference consent, feature activation, custom-code execution or ownership of imported originals       |
| Configure provider/role     | Use provider/profile flow with explicit operation, endpoint identity and data policy; credentials stay in approved facilities  | Probing/billable dispatch without its admission, broader egress, ambient helper execution or fallback |
| Disable                     | Fence new admission and report draining, canceled or unresolved owned work before effective off                                | Uninstall, deletion of data/weights or stopping externally owned services                             |
| Uninstall package           | Review code removed, shared dependency owners and retained assets/data; release only unused owned references                   | Data/model deletion, removal of another module's dependency or external source files                  |
| Delete retained data/assets | Separate scoped confirmation with reference/ownership inventory and authoritative cleanup outcome, usable after module removal | Success before purge/reconciliation or deletion of workspace source/imported originals                |

Install plus enable may be explicitly requested together, as the installation contract permits, but must show two distinct choices and outcomes. The enable choice starts off. Failed enable leaves an honestly installed/off or unconfigured package; successful install alone cannot turn the feature on. Model provisioning and deletion retain separate reviews.

## Screen and interaction proposal

Route labels below are logical destinations for TD-02, not fixed URL paths. Reopening Modules later uses the same review and lifecycle semantics as first launch; no second installer flow is needed.

| Destination      | Content and actions                                                                                                               | Navigation, focus and blocking state                                                                                                                                             |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Setup start      | Base-only explanation, optional selection, skip                                                                                   | Primary base action receives initial focus. Skip/base opens workbench; missing provider gets an inline explanation, never a forced wizard.                                       |
| Module selection | Explicit local/custom Git source choice; cached catalog provenance/freshness, compatible selectable entries, unchecked selections | Back preserves unsent choices in this setup visit. Offline catalog failure offers base-only/skip and a deliberate refresh; it is not an empty successful catalog.                |
| Install review   | Exact selected roots and required dependency closure, pin/digest, trust, rights and costs described below                         | Back/edit invalidates the old review. Cancel closes review without submission and restores its opener. Confirmation is disabled if the engine says the plan is stale or invalid. |
| Operation detail | Correlated accepted/started/progress/outcome, stage, dependency owner and cleanup/recovery details                                | Navigation away retains operation identity and a reachable status link. Back is navigation, not cancellation. Cancel requests cancellation of this operation only.               |
| Modules          | Authoritative installed state plus requested/effective feature state, readiness reason and owned/shared references                | Add, enable, disable, update, rollback and uninstall use the same admitted operations. Unavailable actions explain their missing prerequisite.                                   |
| Recovery         | Prior valid installation, staged failure/uncertain effect, last durable outcome and allowed reconciliation actions                | Retain review inputs as drafts only. Retry is offered only after the engine exposes a safe reconciled action; never silently resubmit.                                           |

The review separates user-selected roots from required dependencies. Each entry shows exact Git source, immutable commit and package path; artifact digest/source binding; license/notice reference; host/API/Windows architecture compatibility; native libraries, services, optional UI assets and separate model needs. A mutable branch name is not the accepted pin. Removing a required dependency means revising/removing its root selection, not hiding the dependency or enabling it automatically. Selection installs only the reviewed closure, never the whole research repository or all model variants.

Show custom/local packages as trusted executable code, with source and integrity distinct from a safety guarantee. Discovery, fetch and prepare do not execute hooks. Any reviewed build/install execution is separately visible in the plan, with its bounded operation/grant admission; accepting package acquisition cannot supply that permission by implication. Changed closure, source bytes, execution requirements or compatibility requires a fresh reviewed plan before effects.

Display app/runtime/WebView provisioning, selected module transfer, installed package/dependency, native and model bytes separately where supplied. Shared assets identify existing owners and incremental versus total cost. An unknown byte count reads **Unknown**, with reason; it never becomes 0 B, an invented total or a completed percentage. Unknown size alone is not fabricated incompatibility: display it and apply the engine's actual validation/capacity outcome. Known-stage progress can be determinate; unknown-total transfer is indeterminate with observed transferred bytes when available. Readiness reads unconfigured, blocked, starting, ready or failed only from the relevant authoritative projection, with tested/unknown/unsupported qualification separate from readiness.

## Setup state machine

These are logical states for TD-29's route fixtures and TD-06's manifests, not route paths or component names. Every state is entered only from the listed trigger; an effect state is left only by an engine outcome, never by the renderer's own timer or optimistic update.

| State        | Entered from (trigger)                                               | Leaves to                                                                  | Guard that must hold                                                                                                  |
| ------------ | -------------------------------------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `start`      | First launch, or Modules reopened                                    | `workbench` (base or skip), `selecting`                                    | No network, catalog, credential or model is needed to leave; zero optional activity on either exit.                   |
| `workbench`  | `start` base/skip, or `recovered` with nothing pending               | `selecting` via Modules                                                    | Reads the authoritative snapshot; reports **Generation unconfigured** without blocking navigation or history.         |
| `selecting`  | `start` choose modules, or Modules add                               | `reviewing`, `workbench`                                                   | Selections start empty; offline or stale catalog shows provenance and a refresh, never an empty successful list.      |
| `reviewing`  | `selecting` confirms roots                                           | `selecting` (edit invalidates the plan), `workbench` (cancel), `operating` | Confirm is disabled unless the engine reports the plan current; any changed pin, closure or compatibility re-reviews. |
| `operating`  | `reviewing` confirm, or an enable, disable, update, uninstall action | `outcome`, `recovering`                                                    | Carries the engine operation identity; Back navigates away without cancelling; Cancel targets this operation only.    |
| `outcome`    | Engine terminal outcome for the operation                            | `workbench`, `selecting`, `recovering`                                     | Shows installed, enabled and ready as three separate facts. Success is shown only from the durable outcome.           |
| `recovering` | Reconnect, engine restart or an uncertain outcome                    | `outcome`, `workbench`                                                     | Shows the prior valid record or an honest staged failure; offers only engine-reconciled actions; never replays.       |

Install, enable, provision and delete are four separate paths through `reviewing` → `operating` → `outcome`. A combined install-and-enable request still produces two reviewed choices and two outcomes. Nothing in `start`, `selecting` or `reviewing` changes installed or effective state.

## Command and outcome input for TD-01

The following are semantic operation proposals, not additional Tauri commands, accepted operation IDs or a new schema. TD-01 alone adopts the minimal allowlisted forms and shared versioned records. Reuse its event envelope and [record contract](implementation-contracts.md#record-contract), TD-15 ordering/cursors, TD-26 transitions and TD-28 installed records. Rust's fixed `handshake`, validated `send`, `cancel`, event subscription and native dialog boundary remain unchanged.

Every submitted action must carry the shared request/correlation identity, authenticated window/scope and applicable expected revisions. Engine acceptance returns the operation identity; subsequent events and the final outcome reference that same identity. Include plan identity/digest for reviewed effects, installed/config revisions for lifecycle changes and scoped retention references for deletion. Exact names/required fields await TD-01. Drafts cannot stand in for an accepted plan or a current grant. Duplicate submission is reconciled by shared command semantics, not another renderer effect.

| User action                        | Proposed admitted intent and prerequisites                                                                                              | Authoritative outcome the GUI must await                                                                                                    |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Continue base / skip               | Navigate to workbench; only an admitted preference save if persistence is needed                                                        | Engine snapshot still reports no optional install/activation; failed preference save is visible without triggering setup effects            |
| Refresh catalog / review selection | Read metadata or resolve selected roots under explicit permitted source access; bind resulting plan to catalog/install/config revisions | Valid review plan, denied, incompatible, offline/unavailable or validation failure; no imported package code                                |
| Confirm installation               | Submit accepted current plan; any executable setup stage has its separate admitted permission                                           | Accepted then staged progress, committed installed record or failed/canceled/uncertain with prior valid record and cleanup state            |
| Enable / disable                   | Request feature transition against current revision and installed prerequisites                                                         | Requested state followed by effective revision/readiness; denied, failed or draining remains visible rather than optimistic success         |
| Import / download model            | Submit separately accepted asset plan; native picker grants only the selected reference, not execution                                  | Owned asset/reference result or failed/canceled/uncertain outcome; provider/feature readiness changes only through its qualified transition |
| Update / rollback                  | Review changed pins/closure and migration/restore compatibility before transition                                                       | Atomic selected record or preserved prior compatible record; incompatible schema blocks rollback with recovery/export choice                |
| Uninstall / delete                 | Submit distinct scoped removal or retention plan with dependency/reference revisions                                                    | Removed code and retained references, or confirmed scoped purge; partial cleanup is incomplete with explicit survivors                      |
| Cancel active operation            | Shared cancel against acknowledged operation identity; local unsent review cancel needs no effect command                               | Cancel requested, then acknowledged canceled/failed/completed/uncertain plus cleanup; clicking cannot prove workers stopped                 |
| Reconnect / restart                | Recover snapshot and durable cursor; explicit Restart only after engine exit under the native process contract                          | Reconciled current records/outcomes; cursor/version mismatch requires resync or visible incompatibility, never effect replay                |

The renderer displays acceptance, start and completion separately. Rejection retains the relevant draft and inline reason. Out-of-order, duplicate, unknown-required or stale-revision events cannot update a different operation or install record. No completion badge precedes the durable outcome; a lost outcome leaves pending recovery/uncertain state. Engine readiness loss disables effect submission but preserves read-only cached views clearly marked stale. Reconnection invalidates old review/approval authority until current identities and revisions are reconciled.

## Gaps in frozen contract v1 for TD-01

[Shared contract v1](shared-contract-v1.md) allowlists no installation or provisioning operation, so the table above stays a proposal. Against the frozen types, TD-01 must add or decide the following before TD-27/28/29 build on it. This is a gap list, not a schema edit.

1. **Operations.** A read-only review/plan request (catalog refresh, closure resolution), an accept-plan install, enable/disable, update/rollback, uninstall, model-asset provision, scoped retention delete, and one cancel addressed by operation identity. `session.cancel` is session-scoped and does not fit.
2. **Events.** No setup or module event kind exists beyond `engine.status` and the reconnect snapshot. Accepted, started, progress (determinate or unknown-total), outcome and recovery events need kinds that carry the operation identity, with outcomes durable and progress transient.
3. **Installation states.** The frozen set is `staging`, `installed`, `failed`, `removing`, `removed`. It has no canceled or uncertain state, so a lost commit or a cancel mid-fetch cannot be expressed honestly; the GUI would have to infer it.
4. **Requested versus effective.** The configuration record has `pending`, `applied`, `draining` and `failed`. That covers requested versus effective for enable and disable, but not "blocked by missing prerequisite", which the Modules screen must show with its reason.
5. **Plan identity.** The installation record has `contentDigest` and `sourceRevisionOrSnapshot` but no reviewed-plan identity or digest. Stale-plan rejection and duplicate-submit reconciliation need one.
6. **Unknown size.** No field distinguishes an unknown byte count from zero. The proposal requires **Unknown** with a reason, so the shape must allow absence plus a reason code.

The ownership split follows [the named case table](team-delivery-plan.md#named-case-ownership): TD-27 builds the planner that produces the reviewed plan, TD-28 owns installed records and recovery, TD-26 owns configuration transitions, TD-29 builds the screens, and TD-08 adapts the client state. No owner here gains authority another already holds.

## Keyboard, failure and recovery contract

- Use labelled semantic controls and the frontend's qualified dialog primitive. Tab follows reading order; Space toggles selections and Enter activates the focused action. Form submission must not accidentally confirm a destructive action or submit during IME composition. Do not add global shortcuts here; TD-02/73 own the catalog.
- Dialogs receive a descriptive heading and focus on the first meaningful non-destructive control. Tab stays inside a modal; Escape dismisses unsent review and restores its opener. Escape/navigation never cancels admitted work or implies deletion. If the opener disappears, restore focus to Modules heading or the surviving operation link. Validation focuses an error summary linked to the offending field without discarding valid inputs.
- Announce status changes through an accessible live region, without stealing focus for progress. Error messages identify stage, affected selection and corrective action, without credentials, stack traces or sensitive locations. Text labels/icons accompany color. Keep selection and error text readable in light/dark/high contrast, reduced motion, keyboard/Narrator, narrow resized windows and 200% scaling; follow dossier contrast and motion constraints.
- Offline metadata/fetch, disk exhaustion, access denial, invalid pin/integrity/compatibility and store-commit failure remain distinct. Retain prior installed/effective state and show owned staging cleanup status. Repair never broadens permissions, substitutes a package/model or deletes user data.
- If interrupted during fetch, prepare, installed-record commit or activation, reopen operation detail from reconciled engine state. It must show the prior valid installation or an honest staged failure, never partially active code. After cancellation or crash, unresolved owned children/cleanup stay visible and block unsafe retry/activation.
- On engine exit, show disconnected status and explicit Restart. Retain unsent selections as drafts, invalidate stale confirmations, recover cursor/snapshot and correlate any late outcome once. Do not reissue install, provisioning, activation or deletion simply because its reply was lost.
- Closing the window follows the native active-work disposition contract. Explain whether owned work will drain/cancel or remain unresolved; window closure is not cancellation acknowledgement. Shared/external services and imported model originals remain outside package cleanup ownership.
